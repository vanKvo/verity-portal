## Objective
Enforce ITAR (International Traffic in Arms Regulations) and Export Control compliance by automating the reconciliation of siloed HR data (Citizenship) against Program Management data (Project Rosters) to detect unauthorized foreign national access to sensitive projects.

## Architectural Principle: Separation of Data Concerns (The "Data Hub" Model)
To prevent compliance risks and enforce strict Separation of Duties, the system utilizes a centralized "Data Hub" model governed by strict Role-Based Access Control (RBAC):
- **Master HR Data (Citizenship & Termination):** Owned exclusively by Human Resources (`ROLE_HR`). Ingested via automated S3 webhook drops or manual upload through a dedicated Data Hub UI. This acts as the single source of truth across all portal modules (ITAR and Leaver).
- **Project Master Data (Sensitivity):** Owned exclusively by Contracts/Legal (`ROLE_CONTRACTS`). They maintain the master list of all projects and their sensitivity classifications (ITAR, EAR, Unclassified).
- **Operational Data (Project Rosters):** Owned by Program Management (`ROLE_PM`). PMs upload temporary assignment rosters to trigger audits, but cannot modify underlying citizenship or project sensitivity.
- **Compliance Enforcement:** Owned by the Export Control Officer (`ROLE_ECO`). Only ECOs have the authority to review, approve, or resolve violations generated by the audit engine.


## Requirement ID: FR-6.1 – Program Management Data Ingestion & Mapping
### Business Context & Rationale (The "Why")
In large enterprises, project assignments are managed in siloed external tools (Jira, MS Project) by Program Managers who do not have access to HR citizenship data. To perform compliance audits without resorting to "Excel engineering", the system must ingest these external rosters and accurately map the many-to-many relationships between personnel and projects within the Verity database.

### User Story
**As an** Export Control Officer,
**I want** to ingest project roster exports from external Program Management tools,
**So that** the system can automatically build an accurate, queryable relationship map of who has access to what, replacing manual Excel cross-referencing.

### Functional Requirements
- **FR-6.1.1: Project Roster Ingestion.** The system shall accept tabular data (CSV/Excel) containing project assignment lists (Employee ID mapped to Project ID).
- **FR-6.1.2: Many-to-Many Mapping.** The system shall dynamically construct or update the many-to-many relationship linking personnel records to project records based on the ingested data.
- **FR-6.1.3: Access Revocation Sync.** The system shall identify records that exist in the database but are missing from the newly ingested active roster, marking their access as revoked/inactive.

### User Interaction & Workflow
#### Path 1: Basic Flow (The Happy Path)
Focus: Successful ingestion of project assignments.
- User navigates to the Intake module and uploads a "Program Management Roster" CSV.
- User utilizes the Shared Mapper to map CSV columns to the `ProjectAssignment` schema.
- System confirms the mapping and ingests the data asynchronously.
- System successfully creates the many-to-many database links between Employees and Projects.
- System displays an "Data Ingestion Complete" summary dashboard.

#### Path 2: Exception Flows (Errors & Edge Cases)
Focus: System-driven failures or invalid inputs.
- **Exc-A: Unrecognized Employee ID:** System encounters an Employee ID in the project roster that does not exist in the Verity HR database. System flags the row as a `Employee does not exist in the HR system`.
- **Exc-B: Unknown Project:** System encounters a Project ID not registered in the system. System flags the record for review and states `Project does not exist in the system`.

#### Path 3: Alternative Flows
Focus: User-driven choices that still result in a valid completion or safe exit.
- **Alt-A: Partial Ingestion:** User chooses to proceed with ingestion despite `MappingErrors` due to missing employee ids or project ids. The system ingests the valid assignments and queues the unrecognized IDs in the "Pending Resolution" bucket.

### Non-Functional Requirements (Constraints)
- **NFR-6.1.1: Performance.** The ingestion service must be able to process and map a roster of 50,000 assignments within 10 seconds.
- **NFR-6.1.2: Idempotency.** Re-ingesting the exact same project roster must not result in duplicate assignment records or database errors.
- **NFR-6.1.3: Security (RBAC).** The ingestion endpoint must be strictly protected by the `ROLE_PM` or `ROLE_ECO` roles to prevent unauthorized data uploads.

### Verification Plan (Acceptance Criteria)
- **AC-6.1.1:** Verify that ingesting a valid roster successfully populates the bridging table between Personnel and Projects.
- **AC-6.1.2:** Verify that re-uploading the same roster updates the `last_verified_date` rather than creating duplicate entries.
- **AC-6.1.3:** Verify that an unrecognized Employee ID is safely caught and flagged without failing the entire batch ingestion.

## Requirement ID: FR-6.2 – HR & Project Master Data Hub (Centralized Ingestion)
### Business Context & Rationale (The "Why")
Data drift from messy system exports (e.g., "US", "U.S.", "United States", "Citizen") prevents automated reconciliation. Utilizing a unified, vertical Data Hub slice decouples data ingestion from modular operational logic (such as ITAR violations and leaver processing). Centralizing S3 ingestion and manual file ingestion under a shared, schema-agnostic Data Hub engine enforces strict schema mapping and validation.

### User Story
**As an** Export Control Officer or HR Administrator,
**I want** the system to automatically ingest and normalize HR citizenship and Project sensitivity records via secure manual mapping and background S3 webhooks,
**So that** I do not have to manually perform database imports or risk unrecognized data bypassing the compliance engine.

### Functional Requirements
- **FR-6.2.1: Custom ENUM Enforcement.** The system shall enforce strict data typing and ENUMs (e.g., `citizenship_status` as `US_CITIZEN`, `PERMANENT_RESIDENT`, `FOREIGN_NATIONAL`; `project_sensitivity` as `ITAR_RESTRICTED`, `EAR99`, `UNCLASSIFIED`) during master data ingestion.
- **FR-6.2.2: Column Header Parsing.** The system shall expose a parsing service to extract unique raw header strings from uploaded files (supporting `.csv`, `.xlsx`, `.xls`, and `.numbers` formats) to present to the user for visual data mapping.
- **FR-6.2.3: Dynamic Mapping Engine.** The system shall allow the user to submit custom key-value JSON column mapping dictionaries (translating arbitrary uploaded header labels to target schema fields) during manual ingestion.
- **FR-6.2.4: Ingestion Normalization.** The ingestion engine shall apply fuzzy-matching dictionaries or pre-defined string mappers to normalize raw input strings into the standard DB ENUM keys.
- **FR-6.2.5: Automated S3 Webhook Routing.** The system shall support background file ingestion triggered by external AWS S3 `s3:ObjectCreated:Put` event webhook drops. The webhook router shall inspect the file's object key and dynamically route execution:
  - If the key contains `"hr"` or `"personnel"`, the file is routed to the **HR Master Ingestor**.
  - If the key contains `"project"`, the file is routed to the **Project Master Ingestor**.
  - Otherwise, the system rejects the file with an `IngestionRoutingError`.
- **FR-6.2.6: Threat-Safe Multi-Format Processing.** The file parser must securely support seekable binary streams and SpooledTemporaryFiles, utilizing temporary file extraction for `.numbers` spreadsheets to prevent event-loop freezing and handle thread-safe file deletion post-parsing.
- **FR-6.2.7: Sync Status & UI Polling.** The system shall expose an endpoint to retrieve the most recent `updated_at` database timestamp across both HR and Project tables. The user interface shall perform periodic background polling (every 10 seconds) and provide a manual refresh action to keep the system status visible.

### User Interaction & Workflow
#### Path 1: Basic Flow (Automated S3 Webhook Ingestion)
Focus: Event-driven background ingestion and standardization of HR master data.
- An external HR system drops the master employee roster spreadsheet (`hr_personnel_records_v5.numbers`) into a secure S3 bucket.
- An S3 event triggers a POST request to the Verity Portal backend webhook (`/data-hub/webhooks/s3-ingest`).
- FastAPI receives the payload, schedules a Background Task, and returns a `200 OK` "S3 Sync Triggered" response immediately to prevent timeout.
- The background task securely downloads the file as a binary stream, writes it to a temporary `.numbers` buffer, parses the rows, and routes them to `PersonnelService` using the dynamic S3 router.
- System processes the upserts, updating the database `updated_at` timestamp.
- The user's active browser page polls `/data-hub/sync-status` and automatically displays the updated "Last Sync: May 22, 2026, 11:43:46 AM" without page reload.

#### Path 2: Exception Flows (Errors & Edge Cases)
Focus: Handling unmappable or malformed background data.
- **Exc-A: Unmappable Status:** System encounters a completely unrecognized citizenship status string. System halts the automated ingestion of that specific record, flags it as a `ValidationError`, and continues ingesting other valid rows to ensure partition tolerance.
- **Exc-B: Routing Failure:** System receives a webhook payload for a file key `inventory/stock_list.xlsx`. The router detects no `"hr"`, `"personnel"`, or `"project"`, raises `IngestionRoutingError`, and halts processing.
- **Exc-C: Malformed S3 Bucket:** The automated worker receives a bucket name containing invalid characters (e.g. underscores) or invalid keys. The `S3EventStrategy` catches the `ClientError` (404 Not Found), raises `DataHubRetrievalError`, and triggers an email alert using `SnsEmailService` to notify administrative staff.

#### Path 3: Alternative Flows
Focus: Manual mapping override for custom spreadsheet uploads.
- **Alt-A: Shared Column Mapper:** An HR Administrator uploads a custom Excel roster file (`new_hires.xlsx`). The frontend extracts headers via `/data-hub/parse-headers`, presents the Shared Column Mapper UI, allowing the user to map "Work Email" to `email` and "National Status" to `citizenship_status`. The user clicks "Upload", sending the file and the mapping schema to `/data-hub/personnel/upload`.

### Non-Functional Requirements (Constraints)
- **NFR-6.2.1: Security (RBAC).** Manual master HR data uploads must require `ROLE_HR` authorization. Manual project master uploads must require `ROLE_ECO` authorization. Webhook calls require internal secure token or AWS IAM credentials.
- **NFR-6.2.2: Auditability.** Any manual override or bulk import must update the target table's audit columns and track execution outputs (success count, error count, row-by-row validation failures).
- **NFR-6.2.3: Non-blocking Async I/O.** The S3 webhook ingestion must execute expensive S3 downloads in an architectural thread pool (`run_in_executor`) to avoid freezing the FastAPI event loop.

### Verification Plan (Acceptance Criteria)
- **AC-6.2.1:** Verify that variations like "US", "USA", and "U.S." map correctly to the `US_CITIZEN` ENUM.
- **AC-6.2.2:** Verify that S3 webhook event triggers run fully in the background and gracefully handle temporary `.numbers` file creation/deletion.
- **AC-6.2.3:** Verify that file keys are correctly routed based on keyword matching, and unmappable keys raise a clear routing error.
- **AC-6.2.4:** Verify that frontend polling queries the max database timestamp and updates the UI status in near-real-time.

## Requirement ID: FR-6.3 – Automated ITAR Reconciliation Engine
### Business Context & Rationale (The "Why")
The core value of the Verity Portal is eliminating manual cross-referencing. By comparing the normalized HR Data (from FR-6.2) against the Program Management Data (from FR-6.1), the reconciliation engine can automatically detect if a foreign national has been granted access to a restricted project in an external system.

### User Story
**As an** Export Control Officer,
**I want** the system to automatically cross-reference the ingested HR and Project data and alert me to mismatches,
**So that** I can immediately identify and remediate ITAR export control violations without having to manually perform VLOOKUPs across spreadsheets.

### Functional Requirements
- **FR-6.3.1: Sensitivity Classification.** The system shall maintain `project_sensitivity` classifications (e.g., ITAR_RESTRICTED, EAR99, UNCLASSIFIED) for all known projects, managed exclusively by `ROLE_CONTRACTS`.
- **FR-6.3.2: Reconciliation Engine.** The system shall execute a batch cross-reference job comparing `citizenship_status` against `project_sensitivity` for all active assignments.
- **FR-6.3.3: Alert Generation.** The system shall generate an actionable compliance alert immediately upon detecting a `FOREIGN_NATIONAL` assigned to an `ITAR_RESTRICTED` project.
- **FR-6.3.4: Auto-Resolution with Audit Trail.** The system shall automatically resolve an open violation during an audit run if updated Master Data (e.g., a citizenship change) resolves the conflict, marking it as `SYSTEM_AUTO_RESOLVED` and preserving the historical audit trail.

### User Interaction & Workflow
#### Path 1: Basic Flow (The Happy Path)
Focus: Automated detection of a compliance violation post-ingestion.
- A Program Manager incorrectly assigned a foreign national to an ITAR-restricted project in Jira (external system).
- Both HR data and Jira data are ingested into the Verity Portal.
- The ITAR Reconciliation Engine runs automatically post-ingestion.
- Engine detects the mismatch between the employee's citizenship and the project's sensitivity.
- System creates a high-priority alert on the Compliance Dashboard.
- Export Control Officer clicks the alert to view actionable details (Employee ID, Project Name, Assignment Date).

#### Path 2: Exception Flows (Errors & Edge Cases)
Focus: Missing metadata during reconciliation.
- **Exc-A: Missing Project Sensitivity:** The Engine encounters an active project assignment, but the project has no defined sensitivity level. System flags the project as "Unclassified - Review Required" to force a classification rather than assuming it is safe.

#### Path 3: Alternative Flows
Focus: Authorized exceptions and Data Corrections.
- **Alt-A: Documented Exception (DSP-5 License):** A foreign national has a specific, documented export license allowing access. An Export Control Officer (`ROLE_ECO`) accesses the violation alert, attaches the license documentation/number, and marks the violation as "Resolved - Licensed Exception".
- **Alt-B: System Auto-Resolution:** HR uploads new Master Data changing an employee's citizenship to `US_CITIZEN`. The next time the PM runs the audit, the system detects the open violation is no longer valid, automatically transitions it to `RESOLVED`, and logs a system resolution reason without deleting the original violation record.

### Non-Functional Requirements (Constraints)
- **NFR-6.3.1: Performance.** The reconciliation engine must be able to scan 100,000+ relationships within 5 seconds to ensure rapid feedback after bulk data ingestion.
- **NFR-6.3.2: Reporting.** Violation alerts must be exportable to PDF and CSV for formal reporting to government auditing agencies.

### Verification Plan (Acceptance Criteria)
- **AC-6.3.1:** Verify that reconciling a US Citizen assigned to an ITAR-restricted project does not generate an alert.
- **AC-6.3.2:** Verify that reconciling a Foreign National assigned to an ITAR-restricted project immediately generates a high-priority alert.
- **AC-6.3.3:** Verify that projects missing sensitivity labels are appropriately flagged for review during the audit run.
